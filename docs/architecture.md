# وثيقة المعمارية الفنية: خط البيانات الهجين (Hybrid Order Data Pipeline)

## 1. الفكرة والمعمارية العامة (ELT Paradigm)

يعتمد المشروع على نمط **ELT (Extract - Load - Transform)** بدلاً من ETL التقليدي. 
الفلسفة الجوهرية لـ ELT في هذا المشروع:
1. **التحميل الأولي الكامل (Raw Ingestion)**: يتم حفظ جميع البيانات الواردة كما هي في طبقة `orders_raw` دون أي تعديل أو تنظيف مسبق، مع إضافة بيانات تتبع (`run_id`, `source_file`, `source_row_number`, `ingested_at`, `engine_used`).
2. **التحويل والتحقق والتصنيف (Transform & Quality Rules)**: بعد استقرار البيانات الخام، يتم تطبيق 9 قواعد فحص وتنظيف آلية وتصنيف كل سجل بدقة.
3. **التحميل النهائي الآمن (Final Load)**:
   - السجلات السليمة والمصححة تنتقل إلى `orders_validated` باستخدام **Idempotent Upsert** ومفتاح الأعمال الثابت `order_id`.
   - السجلات غير القابلة للتصحيح تُعزل في `orders_quarantine` مع رموز الأخطاء والتفاصيل دون أي حذف للبيانات.

```
                           +------------------------+
                           |   Provided Dirty CSV   |
                           +------------------------+
                                       |
                                       v
                         +---------------------------+
                         |        File Router        |
                         | (Threshold: 200 MB / Env) |
                         +---------------------------+
                                  /         \
          Size <= 200 MB         /           \        Size > 200 MB
                                v             v
               +------------------+         +---------------------+
               |   Python Batch   |         |   Apache PySpark    |
               | (Streaming CSV)  |         | (Fixed Schema & DF) |
               +------------------+         +---------------------+
                                \             /
                                 \           /
                                  v         v
                      +----------------------------------+
                      |            orders_raw            |
                      | (Unfiltered raw + run metadata)  |
                      +----------------------------------+
                                       |
                                       v
                      +----------------------------------+
                      |      Quality & Classification    |
                      |   (9 Automated Cleaning Rules)   |
                      +----------------------------------+
                                  /          \
                Valid or Corrected            Unrepairable Errors
                                /              \
                               v                v
                 +-----------------------+   +-------------------+
                 |    orders_validated   |   | orders_quarantine |
                 | (Upsert on order_id)  |   | (Errors & Audit)  |
                 +-----------------------+   +-------------------+
                               |
                               v
                 +---------------------------+
                 |    reports/results.json   |
                 |  (Consistency & Metrics)  |
                 +---------------------------+
```

## 2. المحركات ومعايير التوجيه (File Router)

| المحرك | متى يُختار؟ | آلية العمل | المزايا |
|---|---|---|---|
| **Python Batch** | الملفات $\le$ 200 MB (مثل `orders_small.csv`) | قراءة تدفقية (Streaming) بدفعات قابلة للضبط (`BATCH_SIZE=500`) عبر مكتبة `csv` دون تحميل الملف كاملاً للذاكرة. | خفيف جداً، استهلاك ذاكرة شبه معدوم، إنتاجية عالية (أكثر من 4,000 سجل/ثانية). |
| **Apache PySpark** | الملفات $>$ 200 MB (مثل `orders_huge_mixed_quality.csv` ~12.6 GB) | إنشاء `SparkSession`، قراءة عبر `DataFrame API` بـ Fixed StructType Schema وقراءة جميع الحقول كـ `StringType` لمنع تشويه البيانات المتسخة، ثم معالجة متوازية للأقسام (`Partitions`). | معالجة موزعة حقيقية بدون تحويل لـ Pandas، تستغل جميع أنوية المعالج (CPU Cores). |

## 3. قواعد التنظيف والجودة الآلية (Data Quality Rules)

تم تطبيق 9 قواعد تحويل وتنظيف دقيقة مع حفظ أثر التدقيق الكامل (Audit Trail):

1. **`ARABIC_DIGITS_CONVERT`**: تحويل الأرقام المشرقية `٠١٢٣٤٥٦٧٨٩` وفاصلة الكسر العشرية العربية `٫` إلى أرقام لاتينية قياسية.
2. **`CURRENCY_NORMALIZE`**: إزالة أسماء ورموز العملات المدمجة داخل المبالغ ("ريال", "ريال يمني") وتوحيد حقل العملة إلى `"YER"`.
3. **`THOUSANDS_SEPARATOR_REMOVE`**: حذف فواصل الآلاف (الفواصل الإنجليزية `,` والعربية `،` و `٬`).
4. **`PRICE_WORDS_CONVERT`**: تحويل الكلمات السعرية العربية المحددة إلى قيم رقمية (مثال: "ألفان" $\rightarrow$ 2000.0، "خمسة آلاف" $\rightarrow$ 5000.0).
5. **`PHONE_NORMALIZE`**: إزالة المسافات والرموز الزائدة وتنسيق الرقم اليمني إلى الصيغة الدولية القياسية `+967XXXXXXXXX`.
6. **`EMAIL_REPEATED_SYMBOLS`**: تصحيح الرموز المتكررة في البريد الإلكتروني (مثل `@@` $\rightarrow$ `@` و `..` $\rightarrow$ `.`). وإذا كان البريد تالفاً يُعزل السجل.
7. **`DATE_ISO_NORMALIZE`**: دعم مختلف صيغ التاريخ والوقت (مثل `31/01/2025`, `2025/04/11 13:41:00`, `2025-02-24T21:29:00`) وتحويلها إلى الصيغة المعيارية ISO `YYYY-MM-DDTHH:MM:SS` أو `YYYY-MM-DD`.
8. **`STATUS_SYNONYM_NORMALIZE`**: إزالة المسافات الزائدة وتوحيد المرادفات (مثل "مدفوع" $\rightarrow$ "تم الدفع"، "قيد الدفع" $\rightarrow$ "بانتظار الدفع").
9. **`TOTAL_RECOMPUTED`**: في حال فقدان الإجمالي أو تلفه (`???`)، يتم إعادة حسابه آلياً من مجموع عناصر الطلب (`items_json`) مع تكلفة التوصيل (`delivery_cost`).

## 4. سياسة العزل (Quarantine Policy)

السجلات التي تحتوي على أخطاء لا يمكن تصحيحها بأمان تنتقل إلى `orders_quarantine` مع توثيق الأسباب دون حذف أي سجل:
- `MISSING_ORDER_ID`: غياب معرف الطلب الأساسي.
- `MISSING_CUSTOMER_ID`: غياب معرف العميل.
- `INVALID_IMPOSSIBLE_DATE`: تاريخ غير منطقي أو مستحيل (مثل سنة خارج نطاق 2000-2100 أو نص عشوائي).
- `CORRUPTED_ITEMS_JSON`: نص JSON تالف أو لا يمثل مصفوفة/قاموس صالح.
- `EMPTY_ITEMS`: قائمة عناصر فارغة `[]`.
- `UNKNOWN_PRICE`: السعر مفقود ولا يمكن استنتاجه من العناصر.
- `AMBIGUOUS_NEGATIVE_VALUE`: كميات أو مبالغ سالبة غير محددة المعنى.
- `MULTIPLE_CONFLICTING_ERRORS`: اجتماع 3 أخطاء جوهرية أو أكثر تمنع المعالجة الآمنة.

## 5. الموثوقية وعدم التكرار (Idempotency & Upsert)

- **المفتاح الثابت (Stable Business Key)**: هو `order_id`.
- **الفهارس**: في MongoDB يتم إنشاء `Unique Index` على حقل `order_id` داخل مجموعة `orders_validated`.
- **آلية الـ Upsert**:
  - إذا لم يكن السجل موجوداً: إضافة جديدة (`inserted`).
  - إذا كان موجوداً وتغيرت بياناته: تحديث السجل (`updated`).
  - إذا كان موجوداً وبنفس البيانات تماماً: عدم تعديل (`unchanged`).
- **ضمان الـ Idempotency**: إعادة تشغيل خط البيانات على نفس الملف عدة مرات لا يرفع عدد سجلات الأعمال إطلاقاً في `orders_validated`، ولا يُنشئ أي Duplicate.

---

## 6. معادلة الاتساق الإلزامية (Consistency Equation)

لكل عملية تشغيل (`run_id`)، يتحقق الشرط الرياضي الصارم:

$$\text{run\_raw\_count} = \text{run\_valid\_count} + \text{run\_corrected\_count} + \text{run\_quarantine\_count}$$

ويتم فحص ذلك آلياً وتخزين النتيجة في حقل `raw_consistency_check: true`.

## 7. المسار المتقدم للمجموعات والتميّز الفردي (Path B: Incremental Loading)

ينفذ ملف `src/incremental_loader.py` مسار التحميل التزايدي المتكامل:
1. **تتبع الإصدارات (Version Handling)**: مقارنة إصدار السجل `version` و `updated_at`، ومنع التحديثات المتأخرة (Stale updates) من الكتابة فوق الإصدار الأحدث.
2. **معالجة ملفات Delta**: تطبيق الـ Upsert على السجلات الجديدة والمعدلة فقط.
3. **إثبات الموثوقية عبر 3 تجارب آلية**:
   - التجربة 1: تحميل البيانات الأساسية (`Initial Load`).
   - التجربة 2: معالجة ملف Delta يحتوي سجلات مضافة وسجلات معدلة.
   - التجربة 3: إعادة تشغيل نفس ملف Delta لإثبات أن `inserted_count = 0` وعدد السجلات الإجمالي لم يتغير.
